# Сборка, кэширование и версия

## Зачем нужен nox

`nox` объединяет команды проекта в именованные сценарии — сессии. В нашем случае
они описаны на Python в `noxfile.py`: сборка отчёта, локальный просмотр, измерение
эффекта кэша и проверки корректности.

`Makefile` также подходит для этой задачи. Его сильная сторона — правила зависимостей
между файлами; nox удобен здесь интеграцией с Python и управлением окружениями.
На Windows nox устанавливается через уже используемый `pip`, а Python-команды
в сессиях не зависят от синтаксиса PowerShell или Unix shell.

Каждая сессия создаёт своё окружение в `.nox/`, устанавливает точные версии из
`requirements.txt` и выполняет команду. При следующем запуске окружение используется
повторно; установка проверяет соответствие зависимостей файлу. Первое выполнение
поэтому дольше следующих. Ничего активировать внутри `.nox/` вручную не нужно.

[Документация nox](https://nox.thea.codes/en/stable/tutorial.html).

## Команды

Выполнять из корня проекта, где лежат `noxfile.py` и `mkdocs.yml`.

| Команда | Действие |
| --- | --- |
| `python -m nox -l` | Список доступных сессий |
| `python -m nox -s build` | Подготовка результатов с кэшем и строгая сборка HTML |
| `python -m nox -s serve` | Локальный просмотр; остановка через Ctrl+C |
| `python -m nox -s check` | Проверки кэширования и корректности входных данных |
| `python -m nox -s cache-benchmark` | Первое измерение выигрыша от кэша |
| `python -m nox -s cache-benchmark -- --force` | Повторное измерение с заменой предыдущей таблицы времени кэширования |

Аргументы после `--` передаются скрипту сессии. Команда повторного замера заменяет
только `data/cache_timings.csv` и его JSON; исходные измерения сборки тестовых сайтов
в `data/build_times.csv` сохраняются.

Если нужно проверить обработку, принудительно пропустив кэш, в основном окружении:

```powershell
python scripts/prepare_report.py --no-cache
```

Эта команда пересчитывает результаты, не читая и не записывая кэш. Полные экспериментальные
замеры `benchmark.py` не входят в обычную сборку отчёта и запускаются отдельно.

## Что происходит при сборке

```text
nox build → окружение и зависимости → MkDocs
                                      ↓
                         обработчик перед сборкой
                                      ↓
                  ключ из данных + кода + зависимостей
                         ↙                      ↘
                   кэш найден              кэша нет
                   и проверен            или он повреждён
                       ↓                       ↓
               восстановить файлы      проверить CSV, рассчитать
                                       таблицы, построить график
                                               ↓
                                          сохранить кэш
                         ↘                      ↙
                     свежая метка версии → сборка HTML
```

## Устройство кэша

Результаты сохраняются в `.cache/report/<ключ>/`. Ключ — SHA-256 от содержимого
исходного CSV, его JSON, сохранённого окружения эксперимента, `requirements.txt`,
кода эксперимента, обработки и кэширования, а также версии Python, ОС, архитектуры
и версий библиотек, влияющих на результат.

Ключ зависит от содержимого файлов, а не только от даты изменения. Изменение
измерения, кода расчёта или зависимостей создаёт новый ключ и вызывает пересчёт.
Редактирование текста методики не меняет ключ. Замеры кэширования также не входят
во входные данные самого графика — иначе их сохранение сразу делало бы замер устаревшим.

При попадании в кэш расчёт статистики и построение графика не выполняются; Matplotlib
даже не импортируется. Все сохранённые файлы сверяются с контрольными суммами,
после чего восстанавливаются. Отсутствующий или повреждённый кэш вызывает обычный
пересчёт. Удаление итогового графика из `docs/` также исправляется восстановлением.

| Статус в журнале | Значение |
| --- | --- |
| `MISS` | Подходящего исправного кэша нет; результаты рассчитаны и сохранены |
| `HIT` | Готовые результаты восстановлены; расчёт и построение графика пропущены |
| `BYPASS` | Кэш явно отключён для этого запуска |

Кэш готовых результатов, окружения `.nox/`, кэш загрузок pip и файловый кэш ОС —
разные механизмы. В данном замере оценивается именно кэш подготовки результатов.
Сам nox не реализует наш кэш: это делает модуль `scripts/report_cache.py`.

## Как измеряется выигрыш

Скрипт `scripts/benchmark_cache.py` сначала выполняет один запуск без кэша для
прогрева библиотек и один запуск для заполнения отдельного кэша. Они не входят в
таблицу. Далее запускаются пять обработок с отключённым кэшем и пять с готовым кэшем,
в перемешанном порядке с начальным значением 42.

Измеряется время всего процесса `prepare_report.py`, включая запуск Python и
проверку либо восстановление файлов. Установка зависимостей nox, сборка HTML MkDocs,
сетевые операции публикации и проверка равенства выходных файлов не входят в таймер.
Замер выполняется в отдельной папке `_build/cache-benchmark/`, не меняя страницы
открытого отчёта. После каждого запуска проверяется совпадение всех выходных файлов.

<!-- BUILD_INFO -->

Метки формируются заново при каждой сборке HTML, даже при попадании в кэш результатов.
Они добавляются обработчиком в HTML, а не записываются в исходный Markdown, поэтому
обновление даты не запускает бесконечные пересборки локального сервера.

Хеш обозначает последний коммит исходников. Если есть локальные изменения, метка
явно указывает это: такой сайт может отличаться от сохранённого коммита. Если Git
недоступен и CI не передал хеш, вместо выдуманной версии выводится «не определён».

## Сборка в GitHub Actions

Подготовлен workflow `.github/workflows/pages.yml`: проверки и строгая сборка,
сохранение кэша обработки между запусками и публикация через официальный механизм
GitHub Pages. [Настройка репозитория, устройство workflow и проверки](deployment.md).

На сервере Actions Python и зависимости устанавливаются заранее, поэтому Nox
запускается с `--no-venv`. Обе сессии используют одно окружение временного сервера.
Локально команды без этого флага по-прежнему создают отдельные окружения `.nox/`.

Пользователь подтвердил успешную публикацию GitHub Pages после следующего push;
ошибка первого запуска описана в [журнале отладки](debugging.md).
Workflow также подготавливает отдельный артефакт `helios-site` с адресом Helios.
Передача его файлов на сервер пока выполняется через SFTP вручную.
