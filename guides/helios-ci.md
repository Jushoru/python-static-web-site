# Настройка публикации на Helios

Инструкция для сопровождения проекта. Описание реализации и результаты
публикации находятся в [отчёте](../docs/deployment.md#helios).

## 1. Отдельный ключ для Actions

Для создания ключа на локальном компьютере используется PowerShell:

```powershell
New-Item -ItemType Directory -Force -Path "$env:USERPROFILE\.ssh" | Out-Null
$deployKey = "$env:USERPROFILE\.ssh\helios_report_actions"
ssh-keygen -t ed25519 -C "github-actions-python-static-web-site" -f $deployKey
```

При запросе passphrase дважды нажать Enter: этот отдельный ключ будет
использоваться неинтерактивно. Если файл с таким именем уже существует,
не перезаписывать его — сначала проверить, не создан ли ключ ранее.

| Файл | Назначение |
| --- | --- |
| `helios_report_actions.pub` | Публичный ключ; устанавливается на Helios |
| `helios_report_actions` | Закрытый ключ; хранится локально и в GitHub Environment secret |

Ключ находится вне проекта. Закрытый ключ не нужно добавлять в Git, загружать
в `public_html`, прикладывать к отчёту или публиковать в открытом доступе.

## 2. Разрешить вход этим ключом на Helios

Через текущее SFTP-подключение загрузить **только `.pub`** в домашний каталог:
`/home/studs/s370419/helios_report_actions.pub`.

В SSH-терминале Helios выполнить следующий блок. Он добавляет строку к
существующему `authorized_keys`, сохраняя ранее установленные ключи:

```sh
sh <<'SH'
set -eu
ssh-keygen -lf "$HOME/helios_report_actions.pub"
mkdir -p "$HOME/.ssh"
chmod 700 "$HOME/.ssh"
{
    printf '\nrestrict,command="internal-sftp" '
    cat "$HOME/helios_report_actions.pub"
    printf '\n'
} >> "$HOME/.ssh/authorized_keys"
chmod 600 "$HOME/.ssh/authorized_keys"
SH
```

Параметры `restrict,command="internal-sftp"` ограничивают этот ключ передачей
файлов, отключая интерактивную оболочку и перенаправления. Это **не chroot**:
на уровне сервера ключ всё ещё имеет файловые права учётной записи `s370419`.
В скрипте загрузки зафиксирован путь к каталогу отчёта.
Если сервер сообщает, что параметры ключа не поддерживаются, настройку следует
разобрать по сообщению об ошибке, а не отключать проверку доступа вслепую.

Источник: [формат authorized_keys OpenSSH](https://man.openbsd.org/sshd#AUTHORIZED_KEYS_FILE_FORMAT).

## 3. Зафиксировать ключ самого сервера

Ключ учётной записи разрешает вход. Ключ **сервера** позволяет Actions проверить,
что соединение установлено именно с нужным Helios. Параметры Host и Port нужно
взять из уже работающего SFTP-подключения, а не из веб-адреса `se.ifmo.ru`.

В PowerShell указываются параметры рабочего SFTP-подключения:

```powershell
$heliosHost = 'HOST_ИЗ_РАБОЧЕГО_SFTP'
$heliosPort = 2222 # заменить, если в рабочем подключении другой порт
$knownHosts = "$env:USERPROFILE\.ssh\helios_report_known_hosts"
ssh-keyscan -p $heliosPort -t ed25519 $heliosHost | Set-Content -Encoding ascii $knownHosts
ssh-keygen -lf $knownHosts
```

`ssh-keyscan` только получает ключ; сам по себе он не доказывает его подлинность.
Сверить показанный отпечаток SHA256 с ключом в ранее доверенном подключении.
Например, в уже открытом доверенном SSH-терминале Helios:

```sh
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Оба отпечатка должны совпадать. Если сервер не предлагает Ed25519 или файл по
этому пути отсутствует, нужно уточнить доступный ключ сервера. Не добавлять
непроверенный ключ и не использовать `StrictHostKeyChecking=no`.

## 4. Проверить вход по ключу локально

В том же PowerShell:

```powershell
sftp -P $heliosPort -i $deployKey -o IdentitiesOnly=yes -o BatchMode=yes -o StrictHostKeyChecking=yes -o "UserKnownHostsFile=$knownHosts" "s370419@$heliosHost"
```

В появившейся консоли `sftp>`:

```text
cd /home/studs/s370419/public_html/python-static-web-site
ls
bye
```

Пароль учётной записи запрашиваться не должен. Вход обычным `ssh` с этим ключом
не служит проверкой: ключ специально ограничен SFTP. Если тест не проходит,
не включать автопубликацию до выяснения причины.

## 5. Настроить окружение GitHub

В репозитории открыть **Settings → Environments → New environment**, назвать
его `helios`. В правилах веток публикации разрешить только `main` через
**Selected branches and tags**. Обязательное ручное одобрение не требуется
для выбранного сценария автоматической публикации.

В окружении `helios` добавить **Environment variables**:

| Имя | Значение |
| --- | --- |
| `HELIOS_HOST` | Host рабочего SSH/SFTP-подключения |
| `HELIOS_PORT` | Его порт, записанный числом |

В том же окружении добавить **Environment secrets**:

| Имя | Значение |
| --- | --- |
| `HELIOS_SSH_KEY` | Полное содержимое закрытого `helios_report_actions`, включая строки BEGIN/END |
| `HELIOS_KNOWN_HOSTS` | Содержимое проверенного `helios_report_known_hosts` |

Закрытый ключ можно скопировать без вывода в терминал:

```powershell
Get-Content -Raw -LiteralPath $deployKey | Set-Clipboard
```

Сразу вставить в поле секрета GitHub. Затем скопировать содержимое known_hosts
для второго секрета:

```powershell
Get-Content -Raw -LiteralPath $knownHosts | Set-Clipboard
```

Значения секретов не нужно вставлять в YAML. Workflow получает их только во
время выполнения задания, а скрипт создаёт временные файлы с ограниченными
правами. После завершения загрузки временные файлы удаляются.

Источники: [окружения GitHub](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments),
[секреты GitHub Actions](https://docs.github.com/en/actions/concepts/security/secrets).

## 6. Включить задание и выполнить push

На уровне **репозитория**, а не окружения, открыть
**Settings → Secrets and variables → Actions → Variables → New repository variable**.

```text
Name:  HELIOS_DEPLOY_ENABLED
Value: true
```

Эта переменная проверяется до старта задания, поэтому должна находиться именно
на уровне репозитория. При её отсутствии или другом значении `deploy-helios`
пропускается, а GitHub Pages продолжает работать.

Сохранить изменения workflow, скриптов, тестов и отчёта коммитом и отправить
в `main`. Если файлы уже отправлены до включения переменной, открыть Actions →
Build and deploy report → **Run workflow**, выбрать `main`. Новый пустой коммит
ради запуска не требуется.

В успешном запуске должны завершиться задания `build`, `deploy` и `deploy-helios`.

## Как выполняется загрузка и проверка

`deploy-helios` скачивает артефакт `helios-site` из **этого же запуска**.
Скрипт `scripts/deploy_helios.py` проверяет его структуру и передаёт файлы
стандартным OpenSSH SFTP. На Helios не нужны Python, pip, rsync или программа
сборки. Корневой путь зафиксирован в скрипте:

```text
/home/studs/s370419/public_html/python-static-web-site
```

Ресурсы загружаются перед HTML, затем выставляются права 755 для каталогов и
644 для файлов. Ошибка передачи останавливает задание. Файлы вне каталога
отчёта не являются целями загрузки. Скрипт не удаляет устаревшие файлы: при
удалении страницы из проекта её старую копию на сервере пока нужно убрать
отдельно. Загрузка не атомарна для всего сайта; при обрыве возможен частично
обновлённый отчёт, исправляемый повторным успешным запуском.

После публикации обе площадки проверяются `scripts/check_published.py`:

| Проверка | Что подтверждает |
| --- | --- |
| HTTP 200 главной и `results.html` | Страницы доступны |
| Контрольная строка на главной | По адресу расположен отчёт данного проекта |
| Полный SHA коммита на странице результатов | Опубликована версия этого запуска, а не предыдущая |
| Непустой JSON поискового индекса | Индекс доступен и разбирается |
| Страница теории | Содержит ссылку на актуальную радарную диаграмму |
| Формулы практики | В HTML присутствуют две формулы MathML с номерами |
| График P3, радар PNG и схема JPG | Ресурсы доступны; SVG и сигнатуры PNG/JPEG соответствуют ожидаемым форматам |

Из-за задержек публикации предусмотрены ограниченные повторные HTTP-проверки.
Их не следует путать с повторным запуском всего workflow. Если сайт не прошёл
проверку, задание станет красным; уже переданные файлы автоматически не
откатываются. Работа поискового интерфейса и автономность формул по-прежнему
проверяются отдельно в браузере.

## Проверка автоматического обновления

После первого успеха изменить обычный абзац на главной странице, сделать
коммит и push. Дождаться трёх успешных заданий и проверить новый текст на обеих
площадках. При прежних данных ожидается `Report cache HIT`; отсутствие кэша
тоже допустимо и приводит к пересчёту. Ручная загрузка ZIP на Helios больше
не нужна.
