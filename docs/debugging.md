# Отладка

В этом разделе фиксируются реальные проблемы, возникшие при разработке,
проверенные гипотезы и способы устранения. Предупреждение Material о будущей
версии MkDocs 2.0 не считается ошибкой проекта: сборка с MkDocs 1.6.1
завершается успешно.

## 1. Неверное отображение русского текста в скачиваемом Markdown {#encoding}

### Проявление ошибки

При открытии ссылки на исходный Markdown тестовой страницы браузер показывал
неправильные символы вместо русского текста. Например, заголовок
`# Страница 1` отображался так:

```text
# Ð¡Ñ‚Ñ€Ð°Ð½Ð¸Ñ†Ð° 1
```

Сама HTML-страница с примером отображалась правильно. Ошибка проявлялась при
открытии файла `downloads/example-page.md.txt`. Сообщения об исключении Python
не было: проблема была видна в содержимом страницы браузера.

### Гипотеза

Браузер неправильно определяет кодировку отдельного текстового файла.
Его содержимое записано в UTF-8, но сервер не сообщает эту кодировку явно.

### Проверка

1. Выполнено чтение файла с явным декодированием UTF-8: русский текст оказался корректным.
2. Проверен HTTP-ответ локального сервера: статус `200`, заголовок
   `Content-Type: text/plain` без параметра `charset`.
3. Выполнено сравнение исходного Markdown и скачиваемого примера после декодирования и
   нормализации переводов строк: содержимое совпало.

Таким образом, проблема возникла при определении кодировки отображения,
а не при генерации русского текста или сборке Markdown в HTML.

### Решение

В функции `example_page()` скрипта `scripts/prepare_report.py` изменена запись
скачиваемого текстового файла: используются байты UTF-8 с меткой BOM.

```python
write_if_changed(
    DOCS / "downloads" / "example-page.md.txt",
    sample.encode("utf-8-sig"),
)
```

Метка BOM — байты `EF BB BF` в начале файла — позволяет браузеру определить UTF-8,
даже если сервер не передал кодировку в HTTP-заголовке. Содержимое Markdown
при этом сохраняется. Правка сделана в генераторе, поэтому действует и после
последующих сборок.

### Результат проверки

- Строгая сборка `python -m mkdocs build --strict` завершилась успешно.
- В файле, полученном по HTTP, присутствует метка UTF-8 BOM.
- Текст примера совпадает с исходной тестовой страницей после декодирования
  и нормализации переводов строк.
- После обновления файла подтверждены корректное скачивание
  и отображение русского текста.

## 2. Установка зависимостей Nox в режиме без отдельного окружения {#nox-environment}

### Проявление ошибки

При локальной проверке команды, подготовленной для GitHub Actions,
`python -m nox --no-venv -s check build`, обе сессии завершились ошибкой
до выполнения тестов и сборки:

```text
ValueError: Session check does not have a virtual environment,
so use of session.install() is no longer allowed since it would
modify the global Python environment.
```

### Гипотеза и проверка

Флаг `--no-venv` выбирает текущее окружение Python. Общая функция
`install_dependencies()` безусловно вызывала `session.install()`, который
Nox запрещает в этом режиме. Стек исключения указывал именно на эту строку.
Проверка исходников установленного Nox и документации подтвердила причину.
Ошибка воспроизведена локально при подготовке CI, а не на GitHub.

### Решение

В `noxfile.py` добавлена проверка `session.venv_backend == "none"`:
в этом случае установка внутри сессии пропускается. Workflow предварительно
выполняет `python -m pip install -r requirements.txt` и `python -m pip check`.
Локальные сессии с обычными виртуальными окружениями продолжают сами
устанавливать зависимости.

При дополнительном запуске через полный путь к Python без активации окружения
выявилась зависимость от `PATH`: команда `python` завершалась с кодом 9009.
Поэтому режим без нового окружения явно использует `sys.executable` — тот же
интерпретатор, которым запущен Nox. Обычные сессии используют Python своего
виртуального окружения.

### Проверка исправления

Исправление проверено двумя командами:

```powershell
python -m nox --no-venv -s check build
python -m nox -s check build
```

После исправления обе команды выполнены локально: семь существовавших на этом этапе тестов и строгая
сборка прошли в обоих режимах, подготовка отчёта показала `Report cache HIT`.

Источник: [настройка окружений Nox](https://nox.thea.codes/en/stable/config.html).

## 3. Первый запуск Actions: GitHub Pages недоступен через API {#pages-api}

### Проявление ошибки

В первом запуске workflow шаг `actions/configure-pages@v5` завершился ошибкой:

```text
Error: Get Pages site failed. Please verify that the repository has
Pages enabled and configured to build using GitHub Actions
Error: HttpError: Not Found
```

Задание `deploy` было пропущено (`This job was skipped`). В первом запуске
обработка отчёта показала `MISS`, а в следующем успешном запуске — `HIT`.
Из-за этого возникло подозрение, что публикация требует заранее заполненного кэша.

### Гипотеза и проверка

Проверены шаг, на котором завершился запуск, и порядок шагов в workflow.
Ошибка относится к получению сайта Pages через API. В той версии workflow
`Configure GitHub Pages` выполнялся **после** успешной сборки и сохранения кэша.
Следовательно, `MISS` уже был обработан штатно: результаты рассчитаны и сохранены.
Пропуск `deploy` объясняется зависимостью `needs: build` и ошибкой в задании `build`.

В момент первого запроса сайт Pages не был доступен этому запросу API. Следовало
проверить **Settings → Pages → Source = GitHub Actions**. По одному сообщению
`Not Found` нельзя установить, не была ли настройка включена или ещё не успела
стать доступной; точная причина временного состояния не подтверждена.

### Результат и вывод

После следующего push workflow завершился успешно,
включая `deploy`. Изменять правила кэша для устранения этой ошибки не потребовалось.
`HIT` следующего запуска объясняется сохранением результатов до ошибки Pages.
Сборка с `MISS` также должна успешно публиковаться, если остальные шаги исправны.
Обязательного предварительного неуспешного запуска нет.

[Скриншот неуспешного запуска](deployment.md#failed-run) показывает ошибки
получения настроек Pages. Успешный запуск и попадание в кэш приведены
в [подтверждениях публикации](deployment.md#evidence).

Источник: [настройка источника публикации Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site).

## 4. Ключи Helios записаны в Variables вместо Secrets {#helios-secrets}

### Симптом

Скачивание артефакта `helios-site` завершилось успешно, но шаг SFTP остановился:

```text
Helios upload failed: Set HELIOS_SSH_KEY and HELIOS_KNOWN_HOSTS environment secrets
```

### Гипотеза

Ошибка вызвана отсутствием значений SSH-ключа или known_hosts в окружении задания.

### Проверка

Проверено успешное скачивание артефакта и отсутствие попытки подключения по SFTP.
Имена параметров и раздел их хранения сопоставлены с выражениями в workflow.

### Решение и результат

В окружении `helios` все четыре параметра были записаны в Environment variables.
Workflow получает адрес и порт через `vars`, а ключи — через `secrets`.
Поэтому скрипт получил пустые значения ключей и остановился до подключения.

`HELIOS_SSH_KEY` и `HELIOS_KNOWN_HOSTS` перенесены в Environment secrets;
в Variables оставлены `HELIOS_HOST` и `HELIOS_PORT`. После исправления
деплой завершился успешно. Предупреждения Node.js в том логе не были причиной падения.

## Результаты отладки

Документированы четыре реальные проблемы: кодировка скачиваемого текста,
режим окружения Nox, получение настроек GitHub Pages в первом запуске
и размещение ключей Helios в Variables вместо Secrets.
[Скриншоты неуспешного и успешного запусков, а также подтверждение HIT](deployment.md#evidence)
приведены в разделе публикации.
