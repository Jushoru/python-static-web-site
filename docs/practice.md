# P3. Влияние числа страниц на время сборки MkDocs

## Вопрос исследования

Как изменяются время полной сборки и размер готового сайта при увеличении числа
страниц документации с одинаковой структурой и примерно одинаковым объёмом текста?

## Методика

Эксперимент выполняется скриптом `scripts/benchmark.py` отдельно от сборки отчёта.
Используется один генератор: MkDocs с темой Material и поиском на русском и английском
языках. Все тестовые страницы содержат восемь разделов с текстом, таблицами и кодом.

1. Скрипт создаёт временные сайты на 10, 50 и 100 страниц в каталоге `_build/benchmarks/`.
2. Для каждого размера выполняется одна прогревочная сборка, которая не входит в результаты.
3. Для каждого размера выполняются пять измеряемых сборок. Порядок размеров перемешивается
   с фиксированным начальным значением генератора случайных чисел: 42.
4. Каждая сборка запускается отдельным процессом командой
   `python -m mkdocs build --clean --strict`.
5. Измеряется полное время работы процесса, включая запуск Python и очистку предыдущей
   сборки. Создание исходных Markdown-файлов и подсчёт размера результата в замер не входят.
6. После успешного завершения сохраняются исходные измерения в CSV и параметры среды в JSON.

```powershell
python scripts/benchmark.py --pages 10 50 100 --repeats 5 --dataset-version v1
```

## Как работает скрипт эксперимента

Скрипт `benchmark.py` управляет экспериментом. Он сам создаёт исходные страницы,
запускает установленный MkDocs как отдельную программу и измеряет время её работы.
HTML из Markdown формирует MkDocs, а внешний вид задаёт тема Material.

### Значение параметров команды

| Параметр | Что означает |
| --- | --- |
| `--pages 10 50 100` | Три размера тестового сайта: 10, 50 и 100 страниц, включая главную |
| `--repeats 5` | Пять измеряемых сборок для каждого размера |
| `--dataset-version v1` | Метка набора данных; записывается в CSV и JSON |
| `--output` | Путь для CSV; по умолчанию `data/build_times.csv` |
| `--seed` | Число для воспроизводимого перемешивания порядка запусков; по умолчанию 42 |

Команда выполняет **18 сборок**: три прогревочные и 15 измеряемых. В CSV входят
только последние 15. Прогревочные сборки уменьшают влияние первого чтения файлов
на основные замеры, но не устраняют всю вариативность нагрузки компьютера.

### Создание тестовых страниц

Константа `CONFIG` содержит настройки временного сайта: Material, русский интерфейс,
поиск на русском и английском языках, таблицы и подсветку кода. Константа `SECTION`
задаёт один блок Markdown: подзаголовок, абзац, таблицу и пример кода Python.
Функция `create_fixture()` повторяет этот блок восемь раз на каждой странице.

Каждой странице присваивается свой номер в главном заголовке; остальной текст одинаков.
Это позволяет менять число страниц, сохраняя приблизительно одинаковую нагрузку
от обработки одной страницы. Различия в длине номера заголовка не исключаются.

При десяти страницах получается такая структура:

```text
_build/benchmarks/<идентификатор-запуска>/
    pages-10/
        mkdocs.yml
        docs/
            index.md       # Страница 1
            page-0001.md   # Страница 2
            ...
            page-0009.md   # Страница 10
        site/              # Готовый тестовый сайт
```

[Полный пример страницы](example.md) опубликован отдельно. Можно также скачать
[его Markdown](downloads/example-page.md.txt) и
[конфигурацию временного сайта](downloads/benchmark-config.yml).

**Код внутри страницы не исполняется.** Он является содержимым документа:
MkDocs преобразует его в HTML, а расширение оформляет подсветку синтаксиса.
Числа в таблице примера тоже фиксированы и не являются результатами эксперимента.

### Измерение времени

Функция `run_build()` использует `sys.executable`, чтобы запускать MkDocs тем же
интерпретатором Python и из того же окружения, в котором запущен эксперимент.
`subprocess.run()` ожидает завершения сборки, а `time.perf_counter()` измеряет
прошедшее время с высокой точностью:

```python
started = time.perf_counter()
result = subprocess.run(command, cwd=directory, ...)
elapsed = time.perf_counter() - started
```

Здесь `...` обозначает опущенные параметры записи журнала и переменных окружения;
это поясняющий фрагмент. [Полный скрипт можно скачать](downloads/benchmark.py).

В замер входят запуск Python, загрузка MkDocs, очистка предыдущего результата,
обработка Markdown, применение темы, создание поиска и запись готовых файлов.
Поэтому число в CSV обычно больше времени из сообщения MkDocs
`Documentation built in ...`: эти два таймера охватывают разный объём работы.

После остановки таймера скрипт суммирует размеры всех файлов в `site/`.
Подсчёт размера не увеличивает измеренное время сборки. Если команда завершилась
с ошибкой, эксперимент останавливается и указывает путь к её журналу.

### Повторы и порядок запуска

В `main()` создаются пары «число страниц, номер повтора», затем перемешиваются
через `random.Random(42).shuffle(...)`. Поэтому первая строка прогресса может
показывать `50 pages, repeat 4`: это метка повтора, а не порядковый номер запуска.
Позицию в общей очереди показывает `[1/15]`.

Сборки выполняются **последовательно**, без параллельной нагрузки друг на друга.
Перемешивание уменьшает систематическое влияние постепенного изменения нагрузки
компьютера. Фиксированное значение 42 воспроизводит порядок, но не гарантирует
одинакового времени повторного эксперимента.

При записи окончательного CSV строки сортируются по числу страниц и номеру повтора.
Исходный порядок запусков сохраняется в поле `execution_order` файла JSON.

### Основные части программы

| Часть | Назначение |
| --- | --- |
| `positive_int()` | Проверяет, что число страниц и повторов положительное |
| `create_fixture()` | Создаёт временный проект и Markdown-страницы |
| `run_build()` | Запускает одну сборку, измеряет время и считает размер результата |
| `main()` | Читает параметры, выполняет прогрев и повторы, сохраняет данные и сведения о среде |

JSON также содержит контрольные суммы скрипта и списка зависимостей. Они помогают
установить, какая версия кода и окружения использовалась при получении данных.

## Исходные данные

Основной запуск создал следующие файлы:

- `data/build_times.csv` — 15 строк реальных измерений;
- `data/build_times.metadata.json` — версии инструментов, параметры среды и методика замера.

| Поле CSV | Содержание |
| --- | --- |
| `dataset_version` | Версия набора данных |
| `pages` | Число страниц, включая главную |
| `repeat` | Номер повтора для этого размера |
| `build_seconds` | Измеренное время работы процесса сборки, секунды |
| `site_bytes` | Суммарный размер файлов готового тестового сайта, байты |

Скрипт сохраняет журналы каждой сборки и промежуточные измерения в `_build/benchmarks/`.
Эта папка исключена из Git. Существующий CSV не перезаписывается: для нового набора
нужно указать другое имя через `--output` и новую метку через `--dataset-version`.

## Ограничения

Это полные сборки после прогрева. Файловый кэш операционной системы не очищается,
поэтому результаты нельзя называть измерениями полностью холодной системы.
Здесь также не измеряется инкрементальная пересборка сервера `mkdocs serve`.

Результаты зависят от компьютера, фоновой нагрузки, состава страниц, темы и плагинов.
Они характеризуют выбранную конфигурацию MkDocs и не являются сравнением скорости
четырёх генераторов из T1. Число повторов ограничено; зависимость нужно оценивать
по фактическим данным, учитывая разброс, без предположения о линейном росте.

## Как результаты попадают в отчёт

```text
benchmark.py → исходные измерения CSV + параметры JSON
                           ↓
                   prepare_report.py
                           ↓
           таблицы Markdown + график SVG/PNG
                           ↓
                  MkDocs → сайт-отчёт
```

Сбор измерений и их обработка разделены. Скрипт `scripts/prepare_report.py` читает
сохранённый CSV, проверяет его полноту и группирует строки по числу страниц.
Для каждой группы рассчитываются среднее, медиана, минимум, максимум и выборочное
стандартное отклонение. По результатам Matplotlib строит статический график.

Среднее — сумма времён, делённая на число повторов. Медиана — центральное значение
отсортированного ряда. Выборочное СКО оценивает разброс: из каждого значения вычитают
среднее, возводят разности в квадрат, суммируют, делят на `n − 1` и извлекают корень.
При единственном повторе СКО не оценивается. Для расчётов используются исходные
значения CSV; округление выполняется только при выводе таблицы.

В `mkdocs.yml` подключён `scripts/report_hook.py`. Перед сборкой он запускает
обработку, а затем MkDocs включает полученные страницы и изображения в сайт.
Таким образом, обычные команды работают без отдельного ручного копирования таблиц:

```powershell
python -m mkdocs build --strict
python -m mkdocs serve
```

Первая команда собирает сайт на диске, вторая запускает локальный просмотр.
Обработка повторяется и при пересборке; эксперимент `benchmark.py` автоматически
не запускается. Каталоги `data` и `scripts` добавлены в список наблюдения сервера.
После изменения самого файла обработчика `report_hook.py` сервер нужно перезапустить.

Для отдельной проверки обработки без сборки сайта:

```powershell
python scripts/prepare_report.py
```

[Таблицы, график и исходные материалы доступны на странице результатов](results.md).
Файлы `docs/results.md`, `docs/example.md`, `docs/assets/generated/` и `docs/downloads/`
формируются автоматически: ручные изменения в них будут заменены следующей сборкой.
Текст методики в `docs/practice.md` редактируется вручную.

Механизм запуска описан в [документации MkDocs о hooks](https://www.mkdocs.org/user-guide/configuration/#hooks).
Отрезки разброса построены средствами [Matplotlib errorbar](https://matplotlib.org/stable/api/_as_gen/matplotlib.pyplot.errorbar.html).

## Что ещё предстоит для P3

Обработка CSV и локальная сборка отчёта уже связаны. Кэширование, исключающее
повторный расчёт и построение графика, ещё не реализовано. Пропуск записи неизменившегося
файла предотвращает лишние обновления локального просмотра, но не является кэшем расчётов.

На следующих этапах нужно добавить кэш с измерением выигрыша, запуск конвейера через
`nox`, метки коммита и даты сборки, публикацию на GitHub Pages и Helios, а затем
продемонстрировать обновление опубликованного графика после изменения исходных данных.
